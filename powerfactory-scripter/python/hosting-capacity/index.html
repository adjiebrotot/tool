How to do a hosting capacity study, and automate it in PowerFactory

Hosting capacity is the most new generation (or load) a point of the network can take before a limit is broken: a thermal rating, a voltage limit, a fault level. To find it, connect the new generation at that point and raise it until the first limit breaks; a bisection search does it in about ten load flows. Repeat it at every busbar and you have a hosting capacity map. On PowerFactory's 39-bus example it runs from 8 MW to 1,742 MW, depending on the busbar.

What hosting capacity is

Hosting capacity answers one question for a network owner, a developer or a student: how much can connect here without breaking anything? It is found per connection point and per kind of connection (generation such as solar, wind and batteries exporting, or new load), and depends on the operating state the network is in.

Distribution network service providers publish hosting capacity maps so that applicants see where capacity is left; transmission planners compute it per substation for connection enquiries. The limits that set it are the same everywhere:

  • Thermal: no line, cable or transformer above its rating (at transmission level, also after any single outage).
  • Steady-state voltage: every busbar within its band. Export raises the voltage near the connection, which is what limits rooftop solar on long LV and MV feeders.
  • Voltage step: the change when the new connection trips or connects, often a few percent.
  • Fault level: switchgear still able to break the higher fault current; and for inverters, enough system strength.
  • Protection and power quality: reverse power through a transformer, protection reach and grading, harmonics and flicker.

The first two are found with load flows and are what most hosting capacity studies, and this page, compute. The others are checks on top.

How to do a hosting capacity study

The method does not depend on the software. Every step below is one decision you write down in the study report.

  1. Choose the operating cases. The limit depends on the state of the network: for new generation the hardest case is usually minimum demand with the existing generation high (voltage rise, reverse flow); for new load, maximum demand. Run each case.
  2. Set the limits from the planning standard: the rating each branch may reach and the voltage band each busbar must keep.
  3. Model the connection as a generator at the connection point, at the power factor it will run at (unity here).
  4. Decide where its power goes. In a distribution network the upstream grid takes it (the slack). In a transmission network, other generators turn down: pro rata, as here, or in merit order. This choice changes the answer, so state it.
  5. Search for the largest output that passes. Start from a passing value (0 MW) and a failing one (the most that could ever connect), try the middle, keep the half where the limit lies, and stop when the gap is within the tolerance. From 0 to 2,000 MW with a 5 MW tolerance that is 11 load flows (the two ends and 9 halvings), against 400 for a sweep in 5 MW steps.
  6. Record the hosting capacity and what limited it (the binding constraint), then repeat at every candidate busbar: the result is the hosting capacity map.
  7. Test the sensitivities: another power factor, other demand cases, an outage, the projects already in the queue.

In PowerFactory

The new generation is a static generator (ElmGenstat) connected through a new cubicle (StaCubic) on the busbar, at constant reactive power 0. Each try sets its active power pgini, turns the existing synchronous generators down by the same total, runs ComLdf, and checks c:loading on every line and transformer and m:u on every busbar. Everything is put back and the test generator deleted after each busbar.

hosting_capacity.py

"""Hosting capacity study in PowerFactory with Python: at each busbar, the largest output a new
generator can have before a line or transformer overloads or a voltage leaves its band.

Runs on the "39 Bus New England System" example project that comes with PowerFactory 2024.
"""
import csv
import sys

sys.path.append(r"C:\Program Files\DIgSILENT\PowerFactory 2024\Python\3.12")
import powerfactory

PROJECT = "39 Bus New England System"
STUDY_CASE = "1. Power Flow"
LOADING_MAX = 100.0              # % of rating, every line and transformer
VOLTAGE_BAND = (0.90, 1.10)      # p.u., every busbar
SEARCH_MAX = 2000.0              # MW, the largest output tried
TOLERANCE = 5.0                  # MW, when to stop halving

app = powerfactory.GetApplicationExt()           # inside PowerFactory: powerfactory.GetApplication()
app.ActivateProject(PROJECT)
app.GetProjectFolder("study").GetContents(STUDY_CASE + ".IntCase")[0].Activate()

ldf = app.GetFromStudyCase("ComLdf")
branches = app.GetCalcRelevantObjects("*.ElmLne") + app.GetCalcRelevantObjects("*.ElmTr2")
buses = app.GetCalcRelevantObjects("*.ElmTerm")
# The new generation displaces the generators in service pro rata, so the slack only covers losses.
dispatch = [(g, g.GetAttribute("pgini")) for g in app.GetCalcRelevantObjects("*.ElmSym") if g.outserv == 0]
total = sum(p for g, p in dispatch)


def limits_hold():
    """Run the load flow. (True, "") when every limit holds, else (False, the first one broken)."""
    if ldf.Execute() != 0:
        return False, "load flow does not converge"
    loading, branch = max((o.GetAttribute("c:loading"), o.loc_name) for o in branches if o.outserv == 0)
    if loading > LOADING_MAX:
        return False, f"{branch} loaded to {loading:.0f} %"
    volts = [(b.GetAttribute("m:u"), b.loc_name) for b in buses if b.GetAttribute("m:u") > 0]
    if max(volts)[0] > VOLTAGE_BAND[1]:
        return False, f"{max(volts)[1]} at {max(volts)[0]:.3f} p.u."
    if min(volts)[0] < VOLTAGE_BAND[0]:
        return False, f"{min(volts)[1]} at {min(volts)[0]:.3f} p.u."
    return True, ""


def inject(gen, p_mw):
    """The test generator at p_mw, every other generator turned down by the same total."""
    gen.SetAttribute("pgini", p_mw)
    for g, p in dispatch:
        g.SetAttribute("pgini", p * (1 - p_mw / total))


results = []
for bus in [b for b in buses if b.uknom >= 100]:          # the 345, 230 and 138 kV busbars
    cubicle = bus.CreateObject("StaCubic", "HC cubicle")
    gen = bus.GetAttribute("cpGrid").CreateObject("ElmGenstat", "HC test generator")
    gen.SetAttribute("bus1", cubicle)
    gen.SetAttribute("sgn", 1.5 * SEARCH_MAX)           # MVA, never the limit
    gen.SetAttribute("av_mode", "constq")               # fixed reactive power...
    gen.SetAttribute("qgini", 0.0)                      # ...of zero: unity power factor
    try:
        inject(gen, 0.0)
        ok, why = limits_hold()
        if not ok:
            results.append({"Busbar": bus.loc_name, "Hosting capacity (MW)": 0.0, "Limited by": why})
            continue
        low, high = 0.0, SEARCH_MAX
        inject(gen, high)
        ok, why = limits_hold()
        if ok:
            results.append({"Busbar": bus.loc_name, "Hosting capacity (MW)": high, "Limited by": "nothing up to the search limit"})
            continue
        while high - low > TOLERANCE:                    # halve the gap between pass and fail
            mid = (low + high) / 2
            inject(gen, mid)
            ok, reason = limits_hold()
            if ok:
                low = mid
            else:
                high, why = mid, reason
        results.append({"Busbar": bus.loc_name, "Hosting capacity (MW)": low, "Limited by": why})
    finally:
        for g, p in dispatch:                            # put the dispatch back
            g.SetAttribute("pgini", p)
        app.ResetCalculation()
        gen.Delete()
        cubicle.Delete()

for r in sorted(results, key=lambda r: r["Hosting capacity (MW)"]):
    print(f"{r['Busbar']:7} {r['Hosting capacity (MW)']:7.0f} MW  limited by {r['Limited by']}")

with open("hosting_capacity.csv", "w", newline="") as f:
    out = csv.DictWriter(f, fieldnames=["Busbar", "Hosting capacity (MW)", "Limited by"])
    out.writeheader()
    out.writerows(results)

How the script works

  • Step 2 reads pgini of every synchronous generator, and "Total dispatch" adds them up: the existing generation that will make room.
  • Step 3 loops over the busbars that match CONNECTION_POINT_EL; for this example a filter keeps those with uknom of 100 kV or more.
  • Step 4, Find limit, calls try_n4 with one output after another and halves the gap between GENERATION_LOWER and GENERATION_UPPER down to GENERATION_TOL. A try whose load flow does not converge counts as a fail.
  • Inside each try, add_test_generator connects (or moves) the static generator, "Share kept" works out 1 minus the output over the total dispatch, and Scale sets every generator to that share of its original pgini; pf_undo puts them back after the try.
  • The three checks (LINE_THERMAL_LIMIT_HI, the transformer limit, VOLTAGE_LIMITS_LO and _HI) are combined with And blocks into the pass or fail the search reads.
  • After the search, the busbar's row gets the hosting capacity and the search status; after the loop, the bar chart is drawn and the test generator deleted.

Pitfalls

  • One operating case is one answer. Hosting capacity at minimum demand and at maximum demand can differ several times over. Run the cases that stress each limit, and report the lowest.
  • The balancing rule changes the result. With a single slack taking every megawatt, the slack machine's own transformer soon becomes the "limit" at every busbar. Turn existing generation down (pro rata, as here) or let an upstream grid take it, and say which.
  • Bisection assumes one crossing. It finds the edge between pass and fail when output only makes things worse. If more output first relieves a line and then loads it the other way, check a few points either side of the answer.
  • Check the ratings. c:loading is measured against the rating in the model, the type's rated current times the element's derating. An out-of-date rating gives an out-of-date hosting capacity.
  • Unity power factor is a choice. A connection that absorbs reactive power, or controls voltage, moves the voltage limit a long way: on LV and MV feeders it is often the difference that matters.
  • Leave the network as you found it. Put the dispatch back and delete the test generator and its cubicle after each busbar (after ResetCalculation()), as the script does in finally.
  • Load flow limits are not the whole story. Fault level, protection, voltage step and power quality limits can bind first; treat this result as an upper bound until they are checked.

Questions

What is hosting capacity?

The largest amount of new generation or load that can connect at a point of the network without breaking a limit, such as a thermal rating or a voltage limit, in the operating cases studied.

How is hosting capacity calculated?

Connect the new generation at the point, raise its output, and run a load flow at each step until the first limit breaks. A bisection search finds the edge in about ten load flows. The largest output that passes is the hosting capacity.

What limits hosting capacity?

Usually thermal ratings of lines and transformers and voltage rise; also voltage step on connection, fault level, protection and power quality.

What is a hosting capacity map?

The hosting capacity of every connection point in a network, shown on a map or a chart, often with the limit that binds at each point.

How do I do a hosting capacity study in PowerFactory?

Add a static generator (ElmGenstat) at the busbar, set its pgini, run ComLdf, check c:loading and m:u, and search the largest pgini that passes. The script and the Builder Quick Start on this page do it for every busbar.

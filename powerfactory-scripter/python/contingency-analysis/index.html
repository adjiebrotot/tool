N-1 contingency analysis in PowerFactory with Python

An N-1 screening in Python is a loop: take one line or transformer out of service with SetAttribute("outserv", 1), run the load flow, record the highest loading and the lowest voltage, and put the element back. On PowerFactory's 39-bus example, 18 of 37 outages overload a branch, the worst to 158.3 %.

What N-1 contingency analysis is

The N-1 criterion asks that the network stays within its limits after the loss of any one element: a line, a cable, a transformer or a generator. A contingency analysis checks it by solving the network once per outage. The steady-state screening on this page uses the load flow and two limits: no branch above its thermal rating, and no busbar voltage outside its band.

PowerFactory has a built-in command for it, Contingency Analysis (ComSimoutage), with its contingency cases in ComOutage objects. A Python loop does the same with nothing to set up, and is easy to change: add a check, export a table in your own layout, or run it for every study case.

The method

  1. Run the base case load flow, and record it: an outage is judged against it.
  2. List the outages: every line and network transformer in service (outserv == 0). A generator's own transformer is a loss of generation; study those separately (see Pitfalls).
  3. For each outage, set outserv to 1 and run the load flow. A load flow that does not converge is a result too: record it and go on.
  4. Record the worst values: the highest c:loading of the branches still in service and the lowest m:u of the energised busbars, with where they are.
  5. Put the element back in a finally block, so an error never leaves the project with an outage in it.
  6. Rank the outages by loading and save the table.

The script

contingency.py

"""N-1 contingency analysis in PowerFactory with Python: take each line and network transformer
out in turn, run the load flow, and keep the highest loading and the lowest voltage of each outage.

Runs on the "39 Bus New England System" example project that comes with PowerFactory 2024.
"""
import csv
import sys

sys.path.append(r"C:\Program Files\DIgSILENT\PowerFactory 2024\Python\3.12")
import powerfactory

PROJECT = "39 Bus New England System"
STUDY_CASE = "1. Power Flow"
LOADING_LIMIT = 100.0                               # %

app = powerfactory.GetApplicationExt()              # inside PowerFactory: powerfactory.GetApplication()
app.ActivateProject(PROJECT)
app.GetProjectFolder("study").GetContents(STUDY_CASE + ".IntCase")[0].Activate()

ldf = app.GetFromStudyCase("ComLdf")
branches = app.GetCalcRelevantObjects("*.ElmLne") + app.GetCalcRelevantObjects("*.ElmTr2")
buses = app.GetCalcRelevantObjects("*.ElmTerm")
# A generator's own transformer is left out: losing it loses the generator, a generation
# contingency that needs governor response, not a single slack taking up all of it.
gen_terminals = {g.GetAttribute("bus1").GetParent().GetFullName() for g in app.GetCalcRelevantObjects("*.ElmSym")}
outages = [o for o in branches if o.outserv == 0 and not (
    o.GetClassName() == "ElmTr2" and o.GetAttribute("buslv").GetParent().GetFullName() in gen_terminals)]


def worst():
    """The highest branch loading and the lowest busbar voltage of the last load flow."""
    loading, branch = max((o.GetAttribute("c:loading"), o.loc_name) for o in branches if o.outserv == 0)
    # A busbar cut off by the outage reads exactly 0 p.u.: it is islanded, not low.
    u, bus = min((b.GetAttribute("m:u"), b.loc_name) for b in buses if b.GetAttribute("m:u") > 0)
    return {"Highest loading (%)": loading, "Most loaded": branch, "Lowest voltage (p.u.)": u, "Lowest at": bus}


rows = []
if ldf.Execute() != 0:
    raise SystemExit("The base case load flow does not converge")
rows.append({"Outage": "Base case", "Converged": "yes", **worst()})

for out in outages:
    out.SetAttribute("outserv", 1)                  # take it out of service
    try:
        if ldf.Execute() == 0:
            rows.append({"Outage": out.loc_name, "Converged": "yes", **worst()})
        else:
            rows.append({"Outage": out.loc_name, "Converged": "no"})
    finally:
        out.SetAttribute("outserv", 0)              # always put it back

overloads = [r for r in rows if r.get("Highest loading (%)", 0) > LOADING_LIMIT]
print(f"{len(rows) - 1} outages, {len(overloads)} with a branch above {LOADING_LIMIT:.0f} %")
for r in sorted(overloads, key=lambda r: -r["Highest loading (%)"])[:5]:
    print(f"  {r['Outage']:16} {r['Most loaded']:16} {r['Highest loading (%)']:6.1f} %")

with open("n-1_results.csv", "w", newline="") as f:
    out_csv = csv.DictWriter(f, fieldnames=["Outage", "Converged", "Highest loading (%)", "Most loaded",
                                            "Lowest voltage (p.u.)", "Lowest at"])
    out_csv.writeheader()
    out_csv.writerows(rows)

How the script works

  • Step 2 runs the base load flow; step 3, the Contingency block, gives the base case first and then one pass per line and transformer in service, putting each element back after its pass.
  • Steps 4 to 7 run the load flow and read the highest line loading, the lowest busbar voltage and the highest transformer loading, each with where it is (busbars out of service or not energised are left out).
  • Step 8 adds one row per outage; an outage whose load flow does not converge keeps its row with the reason.
  • After all passes, "Table column" picks the outage with the highest line loading and "Print a message" writes it to the log.

Pitfalls

  • Always put the element back. Set outserv to 0 in a finally block. A script stopped between the two calls leaves the project with the line out of service, and every later study wrong.
  • A single slack takes up every lost megawatt. Taking out a generator's own transformer loses the generator, and on this example the slack machine G 02 then carries it all: its transformer Trf 06 - 31 reaches 211 % when Trf 29 - 38 (G 09) is out. That is the balancing rule speaking, not the network. Study generator outages with a distributed slack or as their own contingency set.
  • Islanded busbars read 0 p.u. An outage that cuts part of the network off leaves its busbars at exactly 0, and IsEnergized() can still return 1 for them after a load flow. Leave out busbars at 0 p.u. when you look for the lowest voltage.
  • A load flow that does not converge is a finding, not an error. Record it and go on: it often means voltage collapse or an island without a reference.
  • Which rating is 100 %? c:loading uses the rating in the model (the type's rated current with the element's derating). Post-contingency short-term ratings are higher: use a different limit, or a separate check, for them.
  • outserv is not switching. It removes the element from the calculation. To model the breakers that clear it, open them (on_off of ElmCoup, or the switch in the cubicle) instead.

Questions

How do I run a contingency analysis in PowerFactory with Python?

Loop over the lines and transformers: SetAttribute("outserv", 1), run app.GetFromStudyCase("ComLdf").Execute(), read c:loading and m:u, then set outserv back to 0 in a finally block.

How do I take an element out of service in a PowerFactory script?

Set its input parameter outserv to 1 with obj.SetAttribute("outserv", 1), and back to 0 to return it to service.

What is the N-1 criterion?

A planning and operating rule: the network must stay within its thermal and voltage limits after the loss of any single element, such as a line, transformer or generator.

Does PowerFactory have its own contingency analysis?

Yes, the Contingency Analysis command (ComSimoutage). A Python loop is a lighter way to the same screening that is easy to adapt; the Builder's N-1 Quick Start writes one for you.

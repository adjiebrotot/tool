Build a PSCAD case and run it from Python

A PSCAD case is not interpreted: it is translated into Fortran, compiled and linked into an executable that EMTDC runs. That is why a script has to build before it runs, why a build error is a compiler error, and why changing a parameter can cost a rebuild. This page is what the build and the run actually do, what the two time steps mean, and how to get the compiler's own words back into your script rather than a traceback.

What building a PSCAD case means

When PSCAD builds a case it writes a Fortran source file for every page of the schematic, calls the Fortran compiler on them, and links the result with the EMTDC libraries into one executable beside the case. The run is that executable; PSCAD only starts it and reads what it writes.

Two things follow, and both show up in a script.

  • A build error is a compiler error. It names a generated Fortran file and a line in it, not your schematic. The usual causes are a component with a parameter it cannot use, a signal wired to nothing, or two signals with the same name on a page. The message is worth putting in your results rather than throwing away.
  • A build is not free. A clean build of a large case is minutes. Most parameter changes do not need one, but anything that changes the generated code does, and PSCAD decides that for itself. A script that runs in a loop should let PSCAD decide rather than forcing a clean build every pass.

There is a third thing worth knowing before the first script: the build leaves a folder beside the case, named after the compiler (mycase.gf46 for GFortran 4.6). It holds the generated Fortran, the object files and the executable, and it is large. Keep scripted cases out of a repository, or ignore that folder.

Building, then running

Build, and read what the compiler said

px_build compiles the case and hands back a result rather than raising: .ok, .errors, .warnings, .messages and .seconds. A case that does not build is a result to record, not a crash.

build = px_build(app, clean=False)

print(build.ok, build.seconds)
for line in build.errors:
    log(line, "warn")
for line in build.warnings:
    log(line)

PSCAD replaces a project's message list at the start of every clean, build and run rather than appending to it, so there is no delta to track: whatever messages() holds after a build belongs to that build.

A clean build, and when it is worth it

clean=True throws the previous build away first. It is the honest thing to do after a component definition has changed, after a library has been swapped, or when a build failure makes no sense; it is wasted time inside a loop.

px_build(app, clean=True)     # first pass: start from nothing
for value in values:
    px_set(load, "P", value, unit="MW")
    px_run(app, duration=2, step=50, plot_step=250)   # builds again only if it has to

The run, and its three numbers

SettingUnitWhat it does
DurationsecondsHow long the simulation runs in simulated time. An EMT run of 5 s is a long run; most studies are under 10 s.
Solution time stepmicrosecondsThe EMTDC step. 50 us is the usual choice. Switching devices and travelling waves want it smaller; it sets how long the run takes more than anything else does.
Channel plot stepmicrosecondsHow often an output channel is written. 250 us is the usual choice. It does not change the solution, only what is recorded, and it is what limits how far up a harmonic spectrum is real.

They are written together, and a script usually writes them once before the loop rather than per run:

sim_settings(app, duration=5.0, step=50, plot_step=250)   # s, us, us

run = px_run(app)                 # or px_run(app, duration=2, step=20, plot_step=100)
print(run.status, run.t_end)
print(run.names())                # every channel the run recorded

A run that stops early is still a result. run.status says why and run.t_end is how far it got, so an unstable case leaves a row saying it went unstable at 1.8 s instead of an exception.

What a run leaves behind, and how it is read

Output channels are written to plain text files beside the case, ten channels to a .out file, with a .inf index naming them in order. A three phase channel becomes three columns, named Desc:1 to Desc:3.

v = run.series("Vpcc")        # by the channel's title, as the .inf index names it
print(v.unit, len(v.t))       # the unit comes from the index, not from a guess

a = run.series("Iline:1")     # one phase of a three phase channel
missing = run.series("Typo")  # an empty Series and one warning, never an error

A channel name the run did not record gives back an empty Series rather than raising, so one wrong name in a long sweep does not lose the rest of the results. The warning says which name, and run.names() lists what was actually there.

How the script works

  • CHECK_ONLY = True at the top connects, finds every component the workflow names, reports what it found and stops before building. Run it that way once on a new case.
  • px_build(app, None, True, False) is the clean build: throw the previous one away, then compile.
  • The build block has two outputs, Built and Did not build, and both are wired. A case that fails to compile leaves a row with the compiler errors in it rather than ending the script.
  • The errors and warnings go into the table as text, so a run over several cases ends with one file saying which built and what the others said.
  • finish(app) in the finally saves the table into a new run folder and writes run.log beside it, whatever happened on the way.

Pitfalls

  • The case builds and the run dies with "is not recognized". Some hardened environments set NoDefaultCurrentDirectoryInExePath, PSCAD inherits it, and so do the batch files EMTDC generates, which call <case>.exe with no path in front of it. Clear that variable for the run; the generated scripts do it for you.
  • A rebuild you did not expect. PSCAD decides for itself whether a change needs the Fortran written again. Writing a parameter that is used at build time triggers one; writing a value that is only read at run time does not. In a sweep this shows up as a few slow passes among fast ones, which is normal.
  • The plot step is not the solution step. Making the plot step smaller records more points and changes nothing about the answer; making the solution step smaller changes the answer and the run time. If a waveform looks coarse, the plot step is the one to change first.
  • A long run with a small plot step writes a lot. Ten seconds at 50 us is 200,000 points per channel. Record what you need and leave the rest of the channels disabled.
  • Build errors scroll past. They are in the project's message list, and PSCAD replaces that list on the next build, so read them into your results on the spot rather than afterwards.
  • Two cases built at once in the same folder collide. Each build writes into the same folder beside the .pscx. Run cases in parallel as a simulation set, or give each its own copy.

Questions

Why does PSCAD have to build a case before running it?

A PSCAD case is translated into Fortran, compiled and linked into an executable that EMTDC runs. The build is that translation and compilation. Anything that changes the generated code needs it done again, and PSCAD works out for itself whether a given change does.

What does a PSCAD build error mean?

It is a Fortran compiler error against the generated source, so it names a generated file and a line, not a part of your schematic. The usual causes are a component given a parameter it cannot use, a signal wired to nothing, or two signals sharing a name on one page.

What time step should I use in PSCAD?

50 us for the solution step suits most power system studies. Power electronics with fast switching, travelling waves and surge studies want smaller. The plot step, which only sets how often a channel is recorded, is usually 250 us and does not change the solution.

How do I read a PSCAD output channel in Python?

Run the case, then read the channel by the title shown on its Output Channel component. The values are written ten channels to a .out file with a .inf index naming them in order, and a three phase channel appears as three columns named Desc:1 to Desc:3.
